# Dexxer

Приватний perpetual DEX для Solana Seeker. Позиція видима лише власнику.

## Архітектура (рішення прийняті 18.09.2026, не переглядати без причини)
- Опція A: власне перп-ядро на шаблоні MagicBlock, НЕ омнібус над Jupiter, НЕ форк Percolator
- Позиція — **делегований** PDA в PER з `EphemeralPermission { is_private, members: [owner, session, crank] }`; нуль комітів на L1 до закриття. На L1 видно лише акаунт під Delegation Program з байтами онбордингу
- Жоден акаунт із полями позиції не комітиться до закриття: `MarketRisk`, `DisclosureQueue` — ніколи; `UserAccount` — лише `free_margin`/`locked_margin`
- Усі **per-user** акаунти (`UserAccount`/`Position`/`DisclosureQueue`) — permissioned `[owner, session, crank]`. **Week 4 факт (ризик #24 закрито, 23.09.2026):** `MarketRisk`+`PoolLive` — permissioned `[crank, admin]` (`init_market_permissions`); `Pool` лишається публічним, але тепер лише огрублений знімок (`SNAPSHOT_STEP`, заповнюється лише `commit_aggregate`) — живі лічильники, які раніше жили в публічному `Pool`/`MarketRisk` в ER (тиждень 3, 22.09.2026, ризик #24: `delegate_pool`/`delegate_market` не створюють `EphemeralPermission`), тепер у приватному `PoolLive`. Публічний агрегат виходить у світ на L1 тільки через 5-хв коміт `Pool`(+`BalancesRoot`, week 3)
- Маржа — облік у приватних `UserAccount`/`Position`, не токени. eATA юзера існує лише на депозит/вивід; open/close не торкаються токен-акаунтів
- Приватність — MagicBlock PER (Intel TDX), не ZK і не FHE. Формулювання: від трекерів, копі-ботів і від нас; не від Intel і не від оператора
- Кастоді — Ephemeral SPL Token (Global Vault на L1 + pool eATA в ER)
- Ціни — Pyth Lazer через MagicBlock Pricing Oracle, mark = EMA над index, ліквідація за mark
- Розкриття — commit-then-reveal через Magic Actions; затримка параметр (демо хвилини, продукт 30 днів)
- Devnet-first: `devnet-tee-as.magicblock.app`, власний `dUSDC` faucet-мінт, пул фондує протокол
- Бекенду, що бачить приватні дані, нема і не буде. Crank — у ER (scheduler), fallback-скрипт зовні — єдиний привілейований сервіс (permission-член), стану не зберігає. **Сервери читають лише публічні акаунти L1/ER і оракул** (рішення 22.09.2026): stateless-індексер для цін/графіків, `Pool`/`BalancesRoot`-снапшотів, L1 `Disclosure`-ленти, push — допустимий; жоден сервіс, крім crank-а, не тримає owner/session-токенів (SIWS-сесії API relayer-а тижня 6 — **не** такі токени: відкривають лише `/sponsor`/`/nonce`, не TEE, у БД лише `sha256`, spec §2.7); приватний стан читає лише клієнт через owner-TEE (`accountSubscribe` замість polling — тиждень 4)

## Правила
- Anchor 1.0.2, Solana 3.1.9, Rust 1.89, `ephemeral-rollups-sdk` 0.16.2 (`anchor`, `access-control`), TS SDK 0.17, `@solana/web3.js` v1 (не kit)
- Округлення — завжди на користь пулу; вся математика в `math.rs`, `u128` проміжні, `checked_*`
- **Приватність = фільтр читання в TEE/QFS, НЕ шифрування** (доки MagicBlock `onchain-privacy`/`local-development`). На L1 фільтра немає → **сирий приватний (permissioned) акаунт ніколи не комітиться на L1 як є** — це зробило б байти публічними; TEE такий коміт не пропускає (ризик №13, підтверджено механізмом і практично — `undelegate_user` теж впала на цьому, week 3, рулінг 10, нижче). Усе, що має вийти на L1, виходить лише через окремий **публічний** похідний акаунт (`Pool`-агрегат, `BalancesRoot`, `Commitment`/`Disclosure` — week 3). Trustless-exit — на публічному `BalancesRoot`-квитанції (без L1-claim, MVP), не на комітах `UserAccount`
- Коміт агрегату — фіксованим інтервалом батчем, ніколи подієво і ніколи на кожну дію. **`commit_aggregate` — єдиний 5-хв bundle: `commit(&[Pool, BalancesRoot])` + post-commit дії з `DisclosureQueue`** (`write_commitment`/`write_disclosure`, week 3; джерело — черга, не `Position`, week 5, див. «Правила тижня 5») — **викликається щоцикл незалежно від наявності дій** (fix round 1, Task 7 тижня 3): фіксований коміт `Pool`+`BalancesRoot` не залежить від того, чи є щось у `remaining_accounts`. Програмна СТЕЛЯ `MAX_ACTIONS_PER_COMMIT = 8` (week 5, було 4), а фактичний бюджет бандла передає клієнт аргументом `commit_aggregate(max_actions)` (фінальне ревʼю week 5, C1) — **живий relayer-дефолт `COMMIT_MAX_ACTIONS = 4`**, бо реальний бридж MagicBlock відхиляє 8 реальних дій (виміряно week 5). `withdraw` містить commit-intent для `UserAccount`, але на devnet-tee він **не долітає до L1 за задумом** (див. правило приватності вище) — гроші рухаються коректно (ER-облік + SPL), лише L1-снапшот `UserAccount` лишається застарілим; це не баг для латання, а сигнал будувати exit на публічному root (реалізовано тижнем 3, `BalancesRoot`)
- Оракул: на кожне читання — feed id, `posted_slot > 0`, staleness, confidence, deviation. Stale → скіп ліквідацій, не ліквідація за старою ціною
- `init_if_needed` не використовувати; `write_commitment` перевіряє escrow-підписанта
- Solana MCP `program_autofixer` на кожну зміну програми до коміту
- Skill `magicblock` — для ER/PER/eSPL/oracle/session keys; `solana-dev` — для Anchor/клієнтів/тестів
- Мова документів і комітів — українська для docs, англійська для коду й commit messages
- `crank_tick` приймає `Config.crank`, `Config.scheduler_signer` або плоский `CRANK_SIGNER`; кандидати ліквідації — `remaining_accounts` **трійками `[Position, UserAccount, DisclosureQueue]`** (week 5, було парами — `DisclosureQueue` потрібна `finalize_close`, що штовхає запис у чергу), ≤16 трійок. **Крank — permission-член кожної позиції** (`[owner, session, crank]`, week 2) — `getProgramAccounts` із crank-токеном повертає приватні акаунти, окремого реєстру кандидатів не потрібно
- **Планувальник (week 2, 21.09.2026):** запланований `crank_tick` підписує Magic Program значенням `crank_signer_pda(admin)` (per-authority PDA, не плоский `CRANK_SIGNER`), яке має лежати в `Config.scheduler_signer` **до** `schedule_crank`. Пишеться окремою base-layer admin-інструкцією `set_scheduler_signer` (`AdminConfig`-патерн, як `pause`/`unpause`) — `schedule_crank` сам більше нічого в `Config` не пише (writable-неделегований акаунт у `ScheduleCrankCpi`'s `instruction_accounts` заборонений безумовно, підтверджено двічі). **`iterations` — кінцеве** (виставляли `86_400` × 1 с ≈ 24 год): планувальник **не вічний**, після вичерпання `mark` застигає — не покладатися на нього як на завжди-онлайн без перезапуску; завжди-онлайн шлях — `crank-fallback`. **Тех-борг №18 — виміряно, розвʼязне (week 3, 22.09.2026, M-D):** `iterations = i64::MAX` приймається й реально тіка́є (81 тік/65 с, спайк-вимір), некостильний фікс без self-reschedule/персистентності; `0`/`-1` FAIL, self-reschedule FAIL при реєстрації, персистентність через рестарт — не виміряно. **Застосовано (week 4, 23.09.2026, Task 7):** `i64::MAX` заведено на реальному розкладі `dexxer_core` (`task_id -8632762600545312817`) — планувальник тіка́є `Market.mark` без relayer (виміряно), але `ScheduleCrank` реєструється без `remaining_accounts`, тож НЕ ліквідує (виміряно): `crank-fallback`/`services/relayer` лишається обов'язковим для ліквідацій незалежно від `iterations`

## Правила тижня 3 (13F-розкриття, `BalancesRoot`, вихід — 21–22.09.2026)
- **Хеш-примітива — keccak256** (`solana_keccak_hasher::hashv`), не sha256 (спека раніше писала sha256 — виправлено); той самий хеш, що вже рахує `salt` у `finalize_close`. Golden vectors спільні для Rust-юніт-тесту й TS (`tests/er/lib/hashes.selftest.ts`, `app/src/lib/hashes.ts`) — пінять байтовий лейаут між мовами
- **Reveal живе всередині `commit_aggregate`, окремої `reveal`-інструкції немає.** `remaining_accounts` (`Position`/`DisclosureQueue`) → `write_commitment` (для `Closed && !commitment_written`) і `write_disclosure` (для due-записів `DisclosureQueue`, через `due_reveals`) — обидва в одному bundle. **(week 5)** `Position`-шлях видалено разом з `mark_committed` — джерело дій тепер лише черга, деталі в «Правилах тижня 5»
- ~~`MAX_ACTIONS_PER_COMMIT = 4`~~ **week 5: піднято до 8** (програмна стеля) — реальний cap мосту на синтетичному спайку тижня 3 виміряно **28 PASS / 29 FAIL** (`0xa0000002`) з дешевшою дією-спайком (5 акаунтів/дію); на реальній формі дій тижня 5 виявився значно нижчим і content-dependent (**8 FAIL / 4 PASS**, деталі в «Правилах тижня 5») — тижня-3 число застаріле для планування бюджету relayer-а
- **`Commitment`/`Disclosure` PDA сідуються хешем commitment-у** (`[SEED, hash]`), не `UserAccount.nonce` — per-user nonce колізує між різними трейдерами на їхньому першому закритті (рулінг 9, знайдено на devnet). `nonce` лишається полем `DisclosureArgs`/`ClosedRecord`, просто не seed
- ~~`mark_committed` — crank-асертований~~ **видалено тижнем 5** (ризик #20 знято разом з інструкцією) — див. «Правила тижня 5»
- **`BalancesRoot` — `#[account(zero_copy)] #[repr(C)]`, НЕ Borsh** — by-value Borsh-десеріалізація 2 KiB-акаунта (`leaves: [[u8;32];64]`) пробивала SBF-стек (LiteSVM `Access violation in stack frame 3`); лейаут `root_slot:u64 | leaves:[[u8;32];64] | version:u8 | filled:u8 | bump:u8 | _pad:[u8;5]`, доступ через `AccountLoader`, не `Account`
- **Будь-яка інструкція, що мутує акаунт і потім undelegate'ить його, мусить викликати `exit()` явно перед CPI, що змінює власника.** Anchor's автоматичний пост-хендлерний `exit()` переписує акаунт уже ПІСЛЯ зміни власника всередині `commit_and_undelegate` → `ExternalAccountDataModified` (рулінг 10, `undelegate_user`, знайдено й виправлено на devnet-tee тижнем 3)
- **Планувальник `i64::MAX`** — виміряно PASS (реально тіка́є), некостильний фікс без self-reschedule/рестарт-персистентності існує; застосовано на реальному розкладі `dexxer_core` (week 4, Task 7, див. вище) — mark-backstop, НЕ ліквідаційний backstop
- **Спостереження (рулінг 8, не підтверджений витік, питання до MagicBlock, ризик #23):** `commit_aggregate`, підписаний лише `Config.fee_payer` (не member жодної `Position`/`DisclosureQueue`), успішно включив приватний акаунт у `remaining_accounts` і виконався на devnet-tee — TEE-permission-шар, схоже, гейтить лише читання через RPC, не tx-інклюзію не-членом. **(week 4)** відтоді навантажений: увесь торговий шлях (`open/close/increase/decrease_position`, що пишуть permissioned `PoolLive`/`MarketRisk` через session/owner-підписантів, які НЕ members) покладається на те саме допущення; fallback, якщо MagicBlock звузить гейт: додати session/owner у members або перевести бухгалтерію на crank-підписаний шлях

## Правила тижня 4 (22–23.09.2026)

- **`PoolLive` — приватний робочий агрегат, `Pool` — лише огрублений знімок.** Усі торгові/грошові інструкції (`open/close/resize`, `deposit`/`withdraw`, `crank_tick`) пишуть **лише `PoolLive`**; `Pool` заповнює **лише `commit_aggregate`**, з огрубленням до `SNAPSHOT_STEP = 100_000_000` (100 dUSDC): активи (`capital_total`/`protocol_liquidity`/`insurance`) — вниз (floor), зобов'язання (`locked_total`/`bad_debt_total`) — вгору (ceil), консервативно для читача забезпеченості
- **`MarketRisk`+`PoolLive` — permissioned `[crank, admin]`** (`init_market_permissions`, ER, ризик #24 закрито).

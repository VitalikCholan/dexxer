# Dexxer — архітектурний документ (Solutions Architecture)

**Дата:** 12 вересня 2026 · **Автор ролі:** solutions architect у Solana-екосистемі · **Статус:** дизайн до першого рядка коду
**Що будуємо:** приватний мобільний перп для Seeker — власне перп-ядро з позиціями в MagicBlock PER (Опція 2, §2.1). Омнібус над зовнішнім venue (Опція 1) лишається як другий адаптер ліквідності для v1.
**Статус розділів:** §0–§2 і §6–§10 актуальні для обох опцій; **§2.1 — цільова архітектура MVP**; §1, §3–§5 описують Опцію 1 і читаються як специфікація зовнішнього адаптера.

## 0. Обмеження, які визначають усі рішення

| Обмеження | Наслідок |
|---|---|
| Соло-розробник, 4 тижні до демо | Кожен компонент — або готовий (venue, PER, MWA), або мінімальний. Жодного власного матчингу, пулу, оракула |
| Приватність без кастодії — головна обіцянка | Ключі ніколи не покидають Seed Vault; жоден сервер не підписує за користувача; бекенд не є точкою відмови для коштів |
| Публічний чейн (Solana), не власний | Пулова модель ліквідності (див. ландшафт 1.7); розподілений матчинг недоступний; account contention — реальність |
| Venue асинхронний (keeper) і ліквідує омнібус як ціле | Request state machine; двошарова ліквідація; ADL-розподіл |
| Мобільний UX | Один тап через Session Keys; push; латентність читання приватного стану < 100 мс |

**Принцип №1:** ончейн-програма — єдине джерело правди для грошей; бекенд — прискорювач і зручність, які можуть впасти без втрат для користувача.
**Принцип №2:** усе, що можна зробити ідемпотентним і повторюваним — робимо таким. Keeper, crank, індексер, push — усі мають переживати рестарт.

## 0.1 Перп-DEX ≠ HFT: який клас системи ми будуємо

Помилка в цій рамці коштує тижнів, витрачених не на ту проблему.

**HFT-рамка працює для venue з власним матчингом.** Hyperliquid, Bullet (0.1 мс), Pacifica (sub-20ms), Lighter змагаються за латентність не з марнославства: маркетмейкер не котируватиме вузький спред, якщо не може швидко скасувати ордер (у HFT-потоці cancel/replace — 90%+ повідомлень). Саме тому всі вони побудували власний шар виконання.

**Пулові venue — не HFT ні в якому сенсі.** Ціна з оракула, матчингу немає, скасовувати нічого. У Jupiter відкриття взагалі асинхронне — і це працює з мільярдними обсягами.

**Dexxer — високодоступний event-driven леджер із м'яким реал-тайм контуром ризику.** Користувач робить одну дію на хвилини або години. Але три шляхи таки чутливі до часу, і плутати їх з рештою небезпечно:

| Шлях | Клас | Вимога |
|---|---|---|
| Ліквідаційний crank | **soft real-time** | Спрацювати раніше за venue: за час, який ціна проходить наш буфер маржі. Секунди, не хвилини |
| Свіжість оракула | soft real-time | Per-market staleness thresholds (урок GMX: 15–280 с залежно від ринку) |
| Котирування викупу | hard real-time | Щойно називаємо ціну — стаємо маркетмейкером, і латентність означає снайп. **Тому вторинки немає в MVP** |
| Решта (відкриття, закриття, читання, історія) | best-effort | Секунда затримки прийнятна |

**Профіль навантаження — не throughput, а корельований сплеск.** Тисяча користувачів по кілька дій на день — тривіальний потік. Проблема: різкий рух ціни → всі закриваються одночасно → crank ліквідує кількох одночасно → і все пише в акаунти, що серіалізуються. Тобто наш клас задачі — **burst під корельованим навантаженням при обмеженні на write-lock**, і лікується він батчингом, пріоритетними чергами, ідемпотентністю й backpressure, а не kernel bypass і колокацією.

**Дві дзеркальні помилки, яких уникаємо:** оптимізувати латентність як HFT (чотири тижні згорять, продукту не буде) і вважати crank звичайним cron'ом раз на хвилину (вичистять у перший волатильний вікенд).

## 1. Архітектура в одному погляді

```
┌──────────────── Мобільний клієнт (Expo / React Native, Android) ────────────────┐
│  MWA connect · Seed Vault підпис (депозит)  · Session Key (трейд)  · push        │
│  читає приватну позицію напряму з PER через QFS (токен = підпис челенджу)        │
└───────────┬─────────────────────────────────────────────────────┬────────────────┘
            │ RPC (власний шар: 2 провайдери, fallback)           │ HTTPS (read-only)
            ▼                                                     ▼
┌───────────────────── Solana base layer ─────────────┐   ┌──── Бекенд (NestJS) ────────────┐
│  Dexxer Core program (Anchor)                       │   │  Indexer (Yellowstone gRPC /     │
│   ├─ UserVault / Margin PDA (публічний, per-user)   │◄──┤   Helius webhooks) → Postgres   │
│   ├─ OmnibusState PDA (агрегат, per market+side)    │   │  Crank runner (BullMQ):          │
│   ├─ SessionToken PDA (expiry, scope, action cap)   │   │   settle_fill · margin check ·   │
│   └─ Venue adapters ── CPI ──► Jupiter Perps /      │   │   internal liquidation ·         │
│                                GMTrade / Flash      │   │   aggregate batcher · disclosure │
│                                    ▲ keeper fill    │   │  Push service (Expo)             │
└────────────────────────────────────┼────────────────┘   │  Compliance gate (Elliptic/Range)│
                                     │                    └──────────────────────────────────┘
┌──────────── MagicBlock PER (TEE, 10–50 мс) ─────────┐
│  UserPosition PDA (приватний: size, side, entry,    │
│   margin, state) — EphemeralPermission: owner+viewer │
│  Pricing Oracle (Pyth Lazer у ER)                    │
│  Commit агрегату на base layer батчами               │
└──────────────────────────────────────────────────────┘
```

**Хто що знає:**
- Venue бачить: одну позицію на сторону від омнібус-PDA.
- Base layer бачить: депозити/виведення користувачів (публічні межі), агрегат омнібусу, session tokens.
- PER бачить: per-user позиції — лише owner і призначені viewer'и.
- Бекенд бачить: події й агрегати; **не бачить приватних позицій** (читає PER лише те, на що має permission — тобто нічого, крім агрегатів).

## 2. Архітектурні підходи: два шляхи до приватного перпа

Є два принципово різні способи отримати приватну позицію з плечем на Solana. Вони розходяться в одному питанні — **де живе позиція**: на чужому venue або в нашій програмі. Від відповіді залежить половина архітектури.

### Опція 1 — Омнібус над чужим venue (детально описана в §1, §3–5)

Наша програма тримає одну агреговану позицію на Jupiter / Flash / GMTrade / Adrena; per-user частки — у PER. Ліквідність чужа, приватність своя.

| + | − |
|---|---|
| Нуль власного капіталу під ризиком; ліквідність мільярдна з першого дня | Позиції на чужому venue → **омнібус обов'язковий**, інакше per-user запис публічний |
| Не будуємо ні пул, ні оракул-інтеграцію, ні страховий фонд | Асинхронний keeper (Jupiter) → request state machine, ціна входу постфактум |
| Не конкуруємо з venue — стоїмо над ним | Venue ліквідує омнібус як ціле → двошарова ліквідація з випередженням |
| Жодного ризику платоспроможності на нас | ADL ріже агреговану позицію → правило розподілу між учасниками |
| | Один омнібус-акаунт → account contention, шардування, батчинг |
| | Залежність від ToS, API і живучості venue (Drift: −$295M за ніч) |

### Опція 2 — Власне ядро перп-DEX + PER

Форкаємо або будуємо власний перп-двигун: пул, маржа, фандинг, ліквідації. Позиції — акаунти **нашої** програми, тому їх можна просто делегувати в PER як окремі приватні PDA. Приватність стає природною властивістю, а не наслідком агрегації.

| + | − |
|---|---|
| **Омнібус не потрібен** — per-user позиції приватні в PER напряму | **Ліквідність наша**: LP або власний капітал під ризиком, страховий фонд, borrow-крива |
| Зникають: request state machine, атрибуція ціни постфактум, двошарова ліквідація, розподіл ADL між чужими частками | Ми — контрагент трейдера; період, коли трейдери мають рацію, — це наш збиток за дизайном |
| Атомарний fill, детермінований стан, повний контроль над ризик-параметрами | Власний оракул-шлях, власні ліквідації, власний бекстоп — усе, що в Опції 1 робив venue |
| Не залежимо від чужого ToS, API, keeper'а | Cold start ліквідності — той самий, що вбив PsyOptions і Friktion |
| Приватність без агрегації → contention лише на стані пулу, не на позиціях | Конкуруємо з Jupiter/GMTrade за трейдерів і LP, а не стоїмо над ними |

**Що лишається спільним для обох опцій:** PER для приватного стану, Session Keys, мобільний фронт, compliance-gate, 13F-розкриття, ліквідаційний crank як soft real-time контур.

### Відхилені варіанти (спільні для обох опцій)

| Варіант | Чому ні |
|---|---|
| **Гібрид з координатором** — бекенд тримає чергу намірів і подає в програму від свого імені | Бекенд стає критичним і напів-кастодіальним; батчинг агрегату беремо як елемент, не як архітектуру |
| **API-first** (модель Bullet, Pacifica) — сервер підписує запити до venue | Прямо суперечить «приватність без кастодії»; агрегація = тримаємо ключ, без агрегації = без приватності |

### Вибір

**Рішення (оновлено, вересень 2026): основна — Опція 2.** Причини, які накопичились після розбору документації MagicBlock і ландшафту:

1. **Ephemeral-акаунти** дають «per-user запису не існує» без омнібусу — остання структурна перевага Опції 1 зникла.
2. **Опція 1 живе лише на мейннеті або на форку з емульованим keeper'ом** (Jupiter Perps на devnet немає), тобто найризикованіша частина — асинхронний fill — саме та, що не тестується чесно. Опція 2 повністю тестується на devnet, де вже є PER, MWA і оракул.
3. **Ризик-двигун у власному ядрі живе всередині ER**; в Опції 1 половина системи лишається на базовому шарі з 400 мс і contention.
4. **Приватність стає властивістю архітектури**, а не наслідком агрегації — це на порядок краще пітчиться і не вимагає ADL-розподілу між чужими частками.
5. **NEAR × Hyperliquid у вересні 2026 зайняв клітинку Опції 1** (Confidential Intents + Chain Signatures над зовнішнім venue) — конкурувати там немає сенсу.

**Гібрид зберігається як рамка:** джерело ліквідності — адаптер, не фундамент. Власне ядро — перша реалізація інтерфейсу; зовнішній venue — друга, для великих позицій у v1, коли буде аудит і капітал. Gate «чи працює CPI до чужого venue» перестає бути блокером демо.

**Умова, за якої рішення валідне:** перевірка №1 з §2.1.12 — чи делегуються акаунти позицій Percolator у PER без переписування слаб-структури. Якщо ні — база не Percolator, а торговий шаблон MagicBlock + математика з `solana-labs/perpetuals` (див. §2.1.11).

## 2.1 Опція 2 у деталях — цільова архітектура MVP

*Розділ написаний після повного розбору документації MagicBlock (ER, PER, Ephemeral Accounts, Ephemeral SPL Token, Magic Actions, оракул, комісії) і ландшафту приватності Solana. Він замінює §1 і §3–5 там, де вони описують омнібус.*

### 2.1.1 Ключова зміна: позиція не існує на базовому шарі

Ephemeral-акаунти MagicBlock — акаунти, які створюються всередині ролапу, живуть і закриваються там, **ніколи не комітячись на Solana**. Це прибирає останню структурну перевагу Опції 1 («per-user запису фізично немає»): тепер її має і власне ядро.

Наслідок для моделі витоків: дія над делегованим акаунтом виконується в ER і **не з'являється на L1**. Раніше документ припускав, що кожна дія лишає слід у базовому шарі — це неправильно для делегованого стану.

### 2.1.2 Розкладка акаунтів

| Акаунт | Тип | Де живе | Комітиться на L1 | Приватність |
|---|---|---|---|---|
| `Market` (параметри, cum_funding, OI-ліміти) | Делегований | ER | Так, батчем | Публічний |
| `Pool` (колатераль, coverage) | Делегований | ER | Так, батчем | Публічний агрегат |
| `UserAccount` (маржинальний баланс, sponsor для ephemeral, лічильник nonce) | Делегований, **sponsor** | ER | Так, рідко | `EphemeralPermission`: власник + session key |
| `Position` (розмір, сторона, вхід, funding_snapshot, salt) | **Ephemeral** | Тільки ER | **Ніколи** | Не існує поза анклавом |
| `ClosedPosition` (до розкриття) | **Ephemeral** | Тільки ER | Ніколи | Власник + аудитор за permission |
| eATA користувача / пулу | Делегований | ER | Рідко | Баланс, не позиція |
| Global Vault (`SPLxh1LV…`) | Звичайний | L1 | — | Публічний, спільний для всієї екосистеми MagicBlock |
| `DisclosureCommitment` (hash) | Звичайний | L1 | Пишеться Magic Action | Публічний хеш, seeds = `[b"commit", nonce]` без owner |
| `Disclosure` (розкритий запис) | Звичайний | L1 | Magic Action через N днів | Публічний |

**Кастоді через Ephemeral SPL Token.** Реальні токени лежать у Global Vault (PDA від `[mint]`), а eATA — легкий запис `u64`, який делегується в ER і мутується там за мілісекунди. Це знімає проблему «програма на L1 не бачить делегованих акаунтів»: маржинальний облік повністю всередині ролапу, токени — на базовому шарі.

**Sponsor — per-user `UserAccount`, не протокольний PDA.** Спільний спонсор став би гарячим акаунтом на кожному `create_ephemeral_position`.

### 2.1.3 Життєвий цикл позиції

| Крок | Де | Що відбувається |
|---|---|---|
| Онбординг | L1 → ER | `deposit` у Global Vault → `delegate(UserAccount)` з прикріпленими **Delegation Actions**: `init_permission` + `set_privacy(true)`. Один підпис MWA замість трьох |
| Відкриття | ER | Перевірка оракула → `create_ephemeral_position` → серіалізація → списання маржі з eATA юзера на eATA пулу |
| Утримання | ER | Crank переоцінює позиції щоблоку; фандинг через кумулятивний індекс |
| Коміт | ER → L1 | Раз на N хвилин: `Pool`, `Market`, зрідка `UserAccount`. **Без розбиття OI на сторони** |
| Закриття | ER → L1 | Розрахунок PnL → `ClosedPosition` з salt → у найближчий коміт додається Magic Action `write_commitment(nonce, hash)` |
| Розкриття | ER → L1 | Через `reveal_after_slot` crank пакетом додає `write_disclosure(...)`; `ClosedPosition` закривається, рента повертається спонсору |
| Вихід | ER → L1 | `commit_and_undelegate` — заборонено, поки є відкриті позиції (cleanup-gate за патерном Sealed-Bid) |

### 2.1.4 Модель витоків — що бачить спостерігач базового шару

Розділ, якого не було в документі; він потрібен і в README, і в деку.

| Момент | Видно на L1 | Приховано |
|---|---|---|
| Депозит | Гаманець, сума, час. Назавжди | — |
| Делегація | Факт користування Dexxer | — |
| Відкриття / зміна / часткове закриття | **Нічого** | Усе |
| Коміт агрегату | Сумарний колатераль пулу, coverage-бакет | Розбиття на сторони, per-user дельти |
| Ліквідація | Факт і момент | Рівень — до настання |
| Закриття | Хеш commitment'у | Вміст до `reveal_after_slot` |
| Розкриття | Ринок, сторона, розмір, вхід, вихід, PnL | Liq-рівень і BE втрачають сенс |
| Вивід | Гаманець, сума. Назавжди | — |

**Що виводиться непрямо:** сумарний PnL за період (`вивід − депозит`); верхня межа позиції (`застава × max leverage`); статистичний розподіл рівнів ліквідації у пулі.

**Обов'язкові мітигації — не оптимізації, а вимоги приватності:**

| Мітигація | Що закриває |
|---|---|
| Коміт **фіксованим інтервалом**, ніколи подієво | Подієвий коміт видає момент і масштаб дії |
| Інтервал **5 хв на старті**, не 30 с | Малий anonymity set: при одному активному юзері дельта = його позиція |
| Уніфіковані номінали депозиту (100/500/1000) | Сума як ідентифікатор, що переживає батч |
| Спільний fee payer / релеєр | Платник лінкує всі дії одного юзера |
| Однакова форма транзакцій для всіх дій | Тип дії читається з набору акаунтів |
| Комісії протоколу — агрегатом, ніколи per-position | Комісія × 1/ставку = розмір позиції |
| Ліквідація в тому ж батчі crank'а, що й планові закриття | Форма транзакції видає тип події |
| `DisclosureCommitment` seeds без owner | PDA від гаманця = «цей юзер закрив позицію зараз» |

**Anonymity set — чесне обмеження.** Приватність батчу пропорційна чужій активності, і на старті її немає. Мітигація: адаптивне вікно коміту при низькій активності. Dummy-операції з власного капіталу — тільки з відкритим документуванням, інакше це роздування обсягу.

### 2.1.5 Розкриття: commit-then-reveal

```rust
// ER, ephemeral
pub struct ClosedPosition {
    owner, market, side, size,
    entry_price, exit_price, pnl,
    opened_slot, closed_slot,
    salt: [u8; 32],          // без солі хеш брутфорситься за хвилини
    mode: DisclosureMode,
    reveal_after_slot: u64,
    nonce: u64,
}

pub enum DisclosureMode {
    Public { delay_slots: u64 },  // дефолт ≈ 30 днів
    Aggregate,                    // лише сумарний PnL за період
    AuditorOnly,                  // на L1 не потрапляє
}

// L1, seeds = [b"commit", nonce]
pub struct DisclosureCommitment { hash: [u8; 32], batch_slot: u64 }

// L1, seeds = [b"disclosure", nonce]
pub struct Disclosure { /* поля ClosedPosition без mode/reveal */ }
```

Перевірка будь-ким: `sha256(Disclosure) == DisclosureCommitment.hash`. Протокол не може підробити історію постфактум.

**Три речі, що ламають схему, якщо їх пропустити:** відсутність солі (мала ентропія полів); owner у seeds commitment'у; `#[action]`-хендлер без перевірки injected escrow-підписанта — інакше будь-хто запише фальшиве розкриття звичайною транзакцією з гаманця.

**Вартість:** два Magic Actions ≈ 25–30k lamports на позицію. Розкриття економічно безкоштовне.

**Чому із затримкою, а не одразу.** Копі-трейдинг працює на живих позиціях, витік стратегії — на свіжій історії. 30 днів вбиває обидва, лишаючи аудитованість. Це модель 13F (лаг 45 днів), а не приховування.

### 2.1.6 Ризик-двигун і crank усередині ER

Ризик-двигун мусить бачити позиції у відкритому вигляді — тому питання «де приватність» і «де ризик-двигун» це одне питання. Відповідь: обидва в TEE.

- **Crank сканує ephemeral `Position`-акаунти всередині ER** — той самий патерн, що `end_auction` у шаблоні Sealed-Bid Auction. Приватність не заважає ліквідації, бо crank у тому самому анклаві.
- **High-precision Scheduling MagicBlock** — crank живе в ролапі як запланована задача, а не зовнішній cron. Урок із `percolator-cli`: одна ітерація на хвилину не встигає при `MAX_ACCRUAL_DT_SLOTS=10` і OI > 0; потрібен внутрішній цикл ~4 с або частіше.
- **Фандинг — кумулятивний індекс на ринку**, `position.funding_snapshot` при взаємодії. Ніколи не ітерувати по позиціях для нарахування.
- **Ліквідація за mark, з гістерезисом.** Порівняння й гілкування всередині TEE — звичайні, без криптографічних витрат. Це те, чого не дають ні ZK (не змусиш неплатоспроможного довести неплатоспроможність), ні FHE (гілкування на шифротексті обчислює обидві гілки).

### 2.1.7 Оракул

Pyth Lazer через MagicBlock Pricing Oracle: оновлення в акаунтах ER кожні **50–200 мс** залежно від активу, проти ~400 мс слотів Solana.

- **Mark ≠ raw print.** При оновленні кожні 50 мс спайки гостріші, не м'якші. Mark = EMA/TWAP над index, рахується crank'ом у ER, де це коштує нуль.
- **Перевірки на кожне читання:** staleness (для перпа поріг 1–2 с, не 60 як у шаблоні Oracle-Priced Purchase), confidence interval, deviation guard проти другого джерела, статус feed'а.
- **Довіра до пушера.** Chain pusher поки закритий (обіцяють відкрити). Мітигація: верифікувати підпис Pyth Lazer у програмі замість довіри пушеру; або deviation guard проти Pyth pull на L1 при коміті.
- **Перевірити на тижні 0:** чи оновлюються оракульні акаунти в **TEE-валідаторі**, а не лише в регіональних ER. Якщо ні — блокер.

### 2.1.8 Ліквідність

Порядок, а не одноразовий вибір:

| Етап | Механізм | Що дає |
|---|---|---|
| MVP | Власний капітал, жорсткі ліміти позиції й OI | Демо працює без зовнішнього капіталу |
| Ядро | **Внутрішній нетинг** лонгів проти шортів | Капітал обслуговує в рази більший обсяг. Найдешевший важіль — закладати одразу |
| v1 | Зовнішній хедж чистої дельти (Jupiter або спот через роутер) | Капітал покриває розрив, а не весь ризик |
| v1 | Senior/junior замість страхового фонду (Percolator) | Прибуток — junior-вимога, депозит — senior; знімає клас сценаріїв неплатоспроможності |
| v2 | RFQ-мейкери в PER (sealed-bid) | Справжній price discovery без публічної книги. Відповідь на тезу Solana Foundation про пулові моделі |

**Приватність самого протоколу.** Хедж-операції на L1 видають агреговану дельту. Мітигації: вікна з випадковим зсувом, розбиття між venue, спотовий маршрут через Jupiter (роутер сам піде в приватні prop-AMM), часткове хеджування. Ключі хедж-гаманців — усередині TEE; фінансування — не прямим трансфером із вольта.

### 2.1.9 Економіка ролапу

| Стаття | Ціна | Примітка |
|---|---|---|
| Транзакція в ER | 0 | Дії користувача безкоштовні |
| Сесія делегації | 300 000 lamports | Списується з депозиту при undelegate |
| Коміт (крім першого) | 100 000 lamports | **Єдина періодична стаття** |
| Live-комісія з 26-го коміту | 100 000 lamports / акаунт | Потрібен delegated fee payer |
| Magic Action | ~10k за 200k CU + 5k callback | Розкриття |
| Ephemeral-сховище | `(bytes + 60) × 32` lamports | Повертається при закритті |

**Інтервал коміту визначає і приватність, і витрати:** 30 с → ~105 SOL/рік на ринок; 5 хв → ~10 SOL/рік. Обидва аргументи тягнуть в один бік.

**Fee payer обов'язковий із тижня 1:** без нього акаунт зупиняється на 11-му коміті з `0xA0000000`. Потрібні `magic_fee_vault`, поповнення через `lamportsDelegatedTransferIx` (свіжа сіль на кожен топ-ап) і ліміти витрат на користувача, щоб один не осушив спільного платника.

### 2.1.10 Модель довіри й відновлення

| Шар | Довіра | Чим підтверджується |
|---|---|---|
| Конфіденційність стану | Intel TDX + оператор ER | `verifyTeeRpcIntegrity` через PCCS Phala — клієнт перевіряє атестацію перед першим запитом |
| Коректність коміту | Fraud-proof + Security Committee | Механізм MagicBlock |
| Кастоді коштів | Програма `SPLxh1LV…` | Не наш код — перевірити аудит, upgrade authority, поведінку вольта при відмові валідатора |
| Доступ до позиції | `EphemeralPermission` | Фільтр на вході TEE, до прийняття транзакції |

**Формулювання, однакове скрізь:** приватність від трекерів, копі-ботів, мисливців за ліквідаціями і від нас — **не від Intel** і не від фізичної атаки на сервер. Це апаратна гарантія, не криптографічна. Той самий корінь довіри використовують Encifher, Inco, Jito BAM і NEAR Confidential Intents — фактичний стандарт категорії.

**Ризик втрати ephemeral-стану.** Смерть ролапу знищує `Position` разом із ним. Маржинальний баланс відновлюється зі стану останнього коміту `UserAccount`; параметри відкритої позиції — ні. Це ціна «не існує на L1», і вона має стояти в README прямим текстом. Для проду: власний TEE-валідатор (репозиторій `magicblock-validator` відкритий, Dstack як середовище) або SLA з оператором.

**Session key мусить бути в members `EphemeralPermission`** — інакше токен доступу до TEE, отриманий підписом session key, не пройде фільтр.

**Magic Router бачить транзакцію до анклаву** (інспектує writable-акаунти й instruction data для маршрутизації). Тому торгові дії — напряму на token-gated TEE-ендпоінт; Router — для публічних L1-операцій. Симуляція для показу ліквідаційної ціни до підпису — явно проти ER-ендпоінту, бо приклади йдуть із `skipPreflight: true`.

### 2.1.11 Тулчейн і порядок збірки

**Версії з PER Quickstart:** Solana 3.1.9, Rust 1.89.0, **Anchor 1.0.2**, Node 24.10.0, `ephemeral-rollups-sdk` ≥ 0.14.

Це змінює оцінку форку: міграція `solana-labs/perpetuals` — не 0.26 → 0.30, а 0.26 → 1.0, через злам IDL у 0.30. Тому **інверсія плану**: не «форкнути перп і додати MagicBlock», а **взяти торговий шаблон MagicBlock і додати перп-математику**.

| Крок | Джерело |
|---|---|
| 1. Зібрати Binary Prediction як є, на `devnet-tee` | Сесії, eATA-кастоді, оракул, crank, коміт — уже зшиті |
| 2. `Bet` → `Position`: розмір, плече, сторона, вхід | Своє |
| 3. Маржинальна математика (IMR/MMR, PnL, liq price) | `solana-labs/perpetuals` / Percolator — **формули, не код** |
| 4. Crank: expiry → перевірка маржі за mark | Своє + Cranks docs |
| 5. Приватність: `init_permission` + `set_privacy` | `private-counter` |
| 6. Приватний `Position` як sponsored PDA + скан у crank'і + cleanup-gate | `sealed-auction` |
| 7. Валідація оракула в ціночутливих інструкціях | `oracle-priced-purchase` |
| 8. Фандинг | Останнім — не критичний для демо |

**MagicBlock Dev Skill** (`npx skills add https://github.com/magicblock-labs/magicblock-dev-skill`) — встановити **першим**: агент без нього галюцинуватиме API, який змінювався щоверсії.

### 2.1.12 Перевірки тижня 0 — у порядку критичності

1. **Структура `Position` у Percolator** — чи це окремий акаунт, чи масив у слабі. Якщо масив — per-user приватність із нього не робиться, Percolator як база відпадає (крейт лишається джерелом математики). *Крейт v16 заявляє «slab-free, account-local» модель ризику — імовірно так, але перевірити в `percolator-prog`.*
2. **Оракул у TEE-валідаторі** — чи оновлюються акаунти Pyth Lazer у `devnet-tee`.
3. **eATA в TEE-валідаторі** — чи працює Ephemeral SPL Token там же.
4. **`EphemeralPermission` на ephemeral-акаунті** — чи можна зробити приватним акаунт, якого немає на L1.
5. **Примусова undelegation після lifetime** — чи може користувач вийти, якщо валідатор мертвий (читати `delegation-program`).
6. **Клонування недалегованих акаунтів у ER read-only** — чи бачить ER-інструкція свіжий стан L1-акаунта.
7. Збірка `private-counter` на власному тулчейні.

### 2.1.13 Дорожня карта слабкостей

Кожна межа рішення має названий спосіб закриття — це окремий слайд у деку.

| Слабкість | Закривається | Коли |
|---|---|---|

### 2.1.14 Що це змінює в конкурентній рамці

Ландшафт зрушив за тиждень до старту, і документ це фіксує:

- **Aster** — другий за обсягом перп-DEX світу; приватний L1 із ZK-шифруванням ордерів, stealth-адресами й Viewer Pass, приватність за замовчуванням. Теза «ніхто не ховає позицію» більше не працює.
- **NEAR × Hyperliquid** — конфіденційні перпи через Confidential Intents (приватний шард FAR + TEE-міст) і Chain Signatures. Це **буквально Опція 1**, реалізована зовні: ховає власника, не позицію (книга Hyperliquid лишається публічною).
- **Paradex** — приватний перп на L3 поверх Starknet: офчейн-книга в одному AWS-регіоні, зашифровані state diff'и на Ethereum, ключі розшифрування в Privacy Council із трьох сторін.

**Нове формулювання тези:** приватний перп уже виграє на інших ланцюгах. На Solana — з найбільшою мобільною аудиторією і Seeker — його немає. Ми не доводимо попит, ми приносимо доведений попит туди, де його не обслуговують.

**Чим Dexxer лишається відмінним:** приховано саме **що** (конфігурація позиції), а не тільки **хто**; без власного ланцюга й токена; мобільний із самокастодією через Seed Vault.

## 3. Компоненти

### 3.1 Ончейн: Dexxer Core (Anchor)

**Акаунти (PDA):**
- `UserVault` — seeds `["vault", owner]`; публічний; тримає депонований USDC/USDT, лічильник вільної маржі, посилання на активну сесію.
- `OmnibusState` — seeds `["omnibus", market, side]`; публічний агрегат: сумарна експозиція, сумарна маржа, coverage ratio, буфер, `pending_delta` для батчу.
- `SessionToken` — seeds `["session", owner, session_pubkey]`; `expiry`, `scope` (bitmask дозволених інструкцій), `actions_left` (ліміт кількості дій — урок GMX One-Click), `max_size`.
- `Request` — seeds `["req", owner, nonce]`; state machine для взаємодії з venue.
- `Disclosure` — seeds `["disc", owner, position_id]`; публічний запис після закриття (13F).

**Інструкції (публічний шар):**
`deposit`, `withdraw`, `create_session`, `revoke_session`, `request_open`, `request_close`, `add_margin`, `settle_fill` (crank), `liquidate_internal` (crank), `commit_aggregate` (crank), `disclose` (crank/owner), `apply_adl` (crank, з обраним правилом розподілу), `pause`/`unpause` (admin, мультисиг + timelock).

**Venue adapters** — окремі модулі за патерном Adapter (див. §5): `jupiter_perps`, `gmtrade`, `flash`. Спільний трейт: `open(delta) → RequestId`, `close(delta) → RequestId`, `read_position() → AggPos`, `fees(size) → Fee`, `staleness_threshold(market)`.

### 3.2 PER (MagicBlock)

- `UserPosition` — seeds `["pos", owner, market]`; делегований у ER з `EphemeralPermission { members: [owner, viewers...] }`; поля: `size`, `side`, `entry_price?`, `margin_allocated`, `state`, `request_id`, `opened_at`, `adl_reduced_by`.
- Ліквідаційний crank виконується **всередині ER** (10–50 мс блоки) з читанням Pricing Oracle — тому per-user перевірка маржі дешева і часта.
- Commit на base layer: **лише агрегат** і лише батчами (кожні N слотів або при зміні > X%) — це і є головна мітигація account contention.

### 3.3 Бекенд (NestJS) — «може впасти»

- **Indexer:** Yellowstone gRPC (Geyser) або Helius webhooks → події програми → Postgres. Джерело для дашборда, push, аналітики. Ідемпотентний за `(signature, event_index)`.
- **Crank runner (BullMQ):** черги `settle-fill`, `margin-check` (тригер з ER), `internal-liquidation`, `aggregate-batch`, `disclosure`. Кожна джоба — ідемпотентна за ключем стану; retry з експоненційним backoff; DLQ.
- **Push service:** Expo Notifications; події `Filled`, `NearLiquidation`, `Liquidated`, `Closed`, `ADLApplied`. Fan-out через чергу, дедуп за `(user, event, position_id)`.
- **Compliance gate:** скринінг адреси при першому депозиті й при виведенні (Elliptic/Range); результат кешується з TTL; гео — на PER-ingress, не тут.
- **RPC:** власний мінімальний шар — два провайдери (Helius + резерв), health-check, перемикання за помилками й таймаутами, OpenTelemetry. Окремі клієнти для ризикового й користувацького контурів.

### 3.4 Мобільний клієнт (Expo/RN)

- MWA для connect і **єдиного** підпису депозиту (approve обмеженому program authority).
- Session Key генерується локально (secure storage), реєструється `create_session`; далі трейди підписуються ним.
- Читання приватної позиції — **напряму з PER через QFS** (токен = підписаний челендж), без нашого бекенду.
- Локальний кеш стану + optimistic UI для `requested → pending`; реконсиляція з подій.
- Push-токен реєструється в бекенді; бекенд не знає позиції — лише що подія сталась для owner'а.

## 4. System design під навантаженням

### 4.1 Де ламається — і чим лікуємо

| Bottleneck | Симптом під навантаженням | Мітигація |
|---|---|---|
| **Account contention на OmnibusState** | Усі дії серіалізуються на одному write-lock; черга в момент різкого руху | Per-user дії пишуть лише у власні PDA (`UserVault`, `Request`, PER `UserPosition`); агрегат оновлює **тільки crank батчем**. Користувацький шлях не торкається `OmnibusState` |
| **Шардинг агрегату** | Навіть батчер стає вузьким при багатьох ринках | `OmnibusState` per `(market, side)` — природні шарди (той самий принцип, що слаби Percolator). Cranks по шардах паралельні |
| **Keeper venue (async fill)** | Pending накопичуються, ціна входу невідома | TTL на `Request` → `expired` з автоповерненням маржі; `settle_fill` читає дельту позиції, не припускає; slippage у кожному request |
| **RPC** | Rate limits, падіння провайдера | Власний шар: два провайдери з health-check і перемиканням; **окремі клієнти для ризикового й користувацького контурів** — UI-трафік не може з'їсти з'єднання, потрібні cranku; читання — з індексера, не з RPC |
| **PER throughput** | Багато `UserPosition` оновлень | Записи в ER дешеві (10–50 мс блоки); тримати позиції як окремі PDA, не масив у одному акаунті |
| **Черга намірів** | Один акаунт черги = той самий write-lock, що й агрегат | **Шардована черга**: N шардів (≈16), користувач потрапляє в `hash(pubkey) % N`. Замість однієї черги — 16 паралельних |
| **Сплеск запитів у пікові хвилини** | Черга росте швидше, ніж обробляється | **Backpressure з асиметрією**: при перевищенні порогу нові **відкриття** відхиляються з чесним повідомленням, **закриття й довнесення маржі пропускаються завжди**. Пріоритет виходу над входом |
| **Push fan-out** | Тисячі нотифікацій за секунду при обвалі | Черга з батчингом до Expo; пріоритет `NearLiquidation` > інше; дедуп |
| **Індексер відстає** | Дашборд показує стале | CQRS: UI показує «стан з блоку N»; критичні дані (позиція) читаються з PER напряму |
| **Compliance API down** | Депозити блокуються | Fail-closed для депозиту, fail-open для виведення (не тримати кошти через збій вендора) + кеш результатів |

### 4.1b Два контури, які не заважають один одному

Фізичне розділення, а не логічне:

| | Контур ризику (soft real-time) | Контур користувача (best-effort) |
|---|---|---|
| Що робить | Читання оракула → перерахунок маржі → внутрішня ліквідація → коміт агрегату | Відкриття, закриття, читання позицій, історія |
| Гарантії | Бюджет часу, не залежить від кількості відкритих застосунків | Може деградувати: користувач почекає секунду |
| Ресурси | Окремі черги, воркери, RPC-з'єднання, ліміти | Окремі |
| Пріоритет у cranku | Ліквідації → закриття → відкриття | — |
| Priority fees | Підвищені під час волатильності | Звичайні |

Правило-інваріант: **UI-трафік не може завадити ліквідації, а робота crank'а не може покласти API.**

### 4.1c API-шар: що і навіщо

| Тип | Для чого | Примітки |
|---|---|---|
| **REST** | Дії (відкрити, закрити, довнести) і запити стану (позиції, історія, параметри ринків) | Запит-відповідь, рідкі виклики, кешується на клієнті |
| **WebSocket** | Живі оновлення: PnL, відстань до ліквідації, переходи `pending → filled`, `near_liquidation`, `adl_reduced` | Обов'язково: **snapshot при підключенні** + дельти, послідовні номери повідомлень, реконект з exponential backoff. Мобільне з'єднання рветься при зміні мережі й згортанні застосунку |
| **Push (Expo Notifications)** | Критичні події, коли застосунок закритий: наближення до ліквідації, fill, ADL | Не альтернатива WS, а інший канал для іншого сценарію. Опційні й відключувані (вимога Publisher Policy) |
| **Вхідні webhooks (Helius)** | Сигнал про зміну омнібус-позиції замість постійного polling'у стану venue | Може не дійти або дійти двічі → ідемпотентність + **резервний polling**. У ризиковому контурі покладатись лише на webhook не можна |
| **Yellowstone Geyser gRPC** | У резерві: потік оновлень акаунтів із меншою затримкою, ніж `accountSubscribe`, якщо WS не вистачить cranku | gRPC **як клієнт до провайдера**, не як наш публічний API |

**Чого немає:** gRPC як публічний API (у RN потребує grpc-web або проксі, виграшу на нашому профілі немає), вихідні webhooks для користувачів (у мобільної людини немає ендпоінта — цю роль виконує push), GraphQL.

**Рішення, яке приймаємо на старті:** WebSocket-сервер — **окремий процес від REST-API**. Тисяча відкритих з'єднань і сплеск HTTP-запитів не повинні заважати одне одному — та сама ізоляція контурів, тільки на рівні транспорту.

### 4.1d Транзакційна механіка Solana: три правила, що стосуються нас напряму

**Priority fees запитуються по write-locked акаунтах, не «взагалі».** `getRecentPrioritizationFees` приймає pubkey'ї акаунтів і повертає `max(мінімальних комісій по цих акаунтах)`. Без параметрів повертає найнижчу комісію для потрапляння в блок — зазвичай нуль, тобто марну оцінку.

Для нас: ліквідаційний crank запитує комісію **саме по омнібус-акаунту (та шарду черги)**, бо це гарячі акаунти, за які конкурують. Інакше в момент волатильності отримаємо нуль і транзакція не пройде саме тоді, коли критично. Ризиковий контур — з підвищеною комісією, користувацький — зі звичайною.

Плюс: явно ставити `setComputeUnitLimit` на реально спожитий CU (виміряти прогоном), а не лишати дефолт — це і дешевше, і краще для throughput.

**Retry безпечний лише після закінчення blockhash.** Повторна відправка транзакції, яка «не виглядає підтвердженою», при живому blockhash — це ризик подвійного виконання. Правило для outbox-воркера: перед retry перевіряти `isBlockhashValid`; поки blockhash живий — чекати, не пересилати. Ключ ідемпотентності захищає логіку від дублювання, `isBlockhashValid` — мережевий рівень.

**Індексер налаштовується під versioned transactions одразу.** `maxSupportedTransactionVersion: 1` і `encoding: "jsonParsed"` з першого дня:
- одна непідтримувана версія в блоці валить увесь `getBlock`, а `getSignaturesForAddress` на версії не падає — тобто без opt-in транзакції v1 видно в списку підписів, але їх неможливо отримати;
- `jsonParsed` включає всі ключі акаунтів (зокрема з lookup tables) у `accountKeys`, тож `preBalances/postBalances` резолвляться без ручної роботи;
- **у форматі v1 compute і fee-ліміти лежать в об'єкті `transactionConfig`, а не в ComputeBudget-інструкціях** — будь-який парсер, що шукає комісії серед інструкцій, покаже для v1 нуль; і v1 не використовує address lookup tables.

### 4.2 Оцінка ємності (MVP → v1)

- **Ончейн:** одна дія користувача = 1 транзакція ~ (1 write у `UserVault` + 1 у `Request` + 1 у PER). Без торкання агрегату — паралельно між користувачами. Ліміт — TPS чейна і CU на транзакцію, не наш дизайн.
- **Crank агрегату:** 1 транзакція на `(market, side)` на батч; при 3 ринках × 2 сторони × батч кожні 2 с — ~3 TPS. Мізер.
- **Ліквідаційний crank у ER:** перевірка маржі per user — O(1) читання; при 10k позицій і блоках 50 мс — прохід усіх за секунди, якщо тримати відсортовану структуру (див. §5).
- **Бекенд:** NestJS + BullMQ на одному інстансі тримає тисячі джоб/с; Postgres із партиціюванням подій по дню. Для хакатону — один контейнер; для v1 — 2 репліки за LB, Redis для черг, read-replica Postgres.

### 4.3 Стійкість

- **Circuit breaker** на кожен зовнішній виклик (venue CPI через staleness check, RPC, Elliptic, Expo).
- **Пауза протоколу** (`pause`) як окрема інструкція під мультисигом із timelock — урок Drift: найбільша загроза — люди з ключами, не код.
- **Idempotency** усюди: crank-джоби за `(request_id, state)`, індексер за `(signature, idx)`, push за `(user, event, id)`. Плюс мережевий рівень: retry транзакції — тільки після закінчення blockhash (`isBlockhashValid`), інакше ризик подвійного виконання.
- **Graceful degradation:** якщо бекенд упав — користувач усе одно може `request_close` і `withdraw` напряму через програму; push не прийде, позиція не постраждає.

## 5. Big O — де складність реально важить

| Операція | Наївно | Цільово | Як |
|---|---|---|---|
| Відкрити/закрити позицію (per user) | O(1) | O(1) | Запис у власні PDA; агрегат не торкається |
| Оновити агрегат | O(n) по користувачах | **O(1)** | Running sums: `total_size += delta`, `total_margin += delta`; ніколи не перераховувати з нуля |
| Перевірка маржі всіх позицій (crank) | O(n) | **O(k log n)**, k — кандидати | Тримати індекс позицій за `liq_price` (heap / відсортований список у ER); перевіряти лише ті, чия ліквідаційна ціна в межах ±δ від поточної |
| Внутрішня ліквідація | O(1) per позиція | O(1) | Один decrease-request + оновлення running sums |
| Розподіл ADL між учасниками | O(n) | O(n), але **рідко** | Один прохід; pro rata за `size` або за левериджем; батчами по m користувачів на транзакцію через `remaining_accounts` |
| Нетинг лонг/шорт (v1.1) | O(n²) наївно | O(n) | Дві running sums; нетиться різниця, не пари |
| Читання позиції користувачем | O(1) | O(1) | Прямий read PDA з PER через QFS |
| Пошук sessions/requests користувача | O(n) скан | O(1) | Детерміновані seeds — адреса обчислюється, не шукається |
| Індексер: агрегати для дашборда | O(n) на запит | O(1) | Матеріалізовані в'ю / інкрементальні лічильники в Postgres |

**Чому звична нотація тут обманює.** Ончейн вартість вимірюється не лише кроками алгоритму, а **кількістю акаунтів у транзакції** (≈64 максимум, і кожен write-lock — це серіалізація) та **compute units** (200k за замовчуванням, до 1.4M із запитом). Дві типові пастки:
- інструкція, що приймає вектор користувачів і йде по ньому циклом: виглядає прийнятно для n=50, але впирається в ліміт акаунтів і CU. Правильно — **фіксований батч 8–16 позицій на транзакцію**, великий обсяг кількома транзакціями;
- пошук ліквідаційних кандидатів лінійним скануванням: при 1k позицій і cranku кожні кілька секунд це тисячі читань за цикл. **Бакети за ліквідаційним порогом** зводять це до десятків.

**Розміри акаунтів (rent):** `UserPosition` ~120 байт; `Request` ~96; `SessionToken` ~80; `OmnibusState` ~160. Рахувати `space` явно, `#[account(zero_copy)]` для гарячих акаунтів, версійне поле `version: u8` у кожному для міграцій.

**Compute units:** CPI у venue — найдорожча інструкція (~100–200k CU з коду Jupiter); власна логіка тримати < 50k CU; ліквідаційний crank у ER — окремий бюджет, не base layer.

## 6. Design patterns — які і навіщо

| Патерн | Де | Навіщо |
|---|---|---|
| **Adapter** | Venue adapters (`jupiter_perps`, `gmtrade`, `flash`) | Додати venue = додати модуль; ядро не знає деталей venue. Урок Cookbook у RAILGUN |
| **State Machine** | `Request`: `requested → pending → filled \| failed \| expired`; `UserPosition`: `open → reducing → closed → disclosed` | Асинхронний keeper без гонок; кожен перехід — окрема інструкція з guard'ами |
| **Strategy** | Правило розподілу ADL (`ProRataBySize`, `ByLeverage`, `FIFO`) | Обране заздалегідь, змінюється конфігом, описане в умовах |
| **Saga / Compensation** | `request_open` → (keeper fill) → `settle_fill`; при `expired` — компенсація повертає маржу | Немає атомарності між нами й venue — потрібні компенсуючі кроки |
| **Outbox + Event Sourcing** | Програма емітить події (`anchor emit!`); індексер будує стан із подій | Бекенд відновлюється з нуля з подій; жодного «істинного» стану в Postgres |
| **CQRS** | Записи — в програму; читання — з індексера (публічне) або з PER (приватне) | Розділяє гарячий шлях запису й важкі читання |
| **Circuit Breaker** | Власний RPC-шар; staleness-check перед CPI; compliance-вендори | Не тягнути падіння залежностей у критичний шлях |
| **Idempotent Consumer** | Усі crank-джоби й індексер | Рестарт без дублювання дій |
| **Batching** | `commit_aggregate` кожні N слотів; ADL по m користувачів на tx; push до Expo | Головна відповідь на account contention і rate limits |
| **Backpressure (асиметричний)** | Поріг глибини черги: нові відкриття відхиляються, закриття й довнесення маржі пропускаються завжди | Пріоритет виходу над входом — базове правило ризикових систем |
| **Sharding** | `OmnibusState` per `(market, side)`; черга намірів на ≈16 шардів за `hash(pubkey)` | Паралельні cranks, менший blast radius, обхід write-lock contention |
| **Bulkhead** | Окремі черги, воркери й RPC-клієнти для ризикового й користувацького контурів; окремий процес WS від REST | Затор у push не блокує ліквідації; UI-сплеск не забирає з'єднання в crank'а |
| **Pending → apply → available** | Надходження маржі: вхідні кошти спершу в «очікувану» зону, явна дія переводить у доступну | Патерн підтверджений стандартом Token-2022 Confidential Balances; розв'язує асинхронне надходження при детермінованому обліку — та сама форма, що наша request state machine |
| **Time-to-live** | `Request.expiry`, `SessionToken.expiry` | Нічого не висить вічно |
| **Capability tokens** | `SessionToken` зі scope + action cap | Мінімальні права на мінімальний час |
| **Guard / Precondition** | Кожна інструкція перевіряє `state`, `expiry`, `scope`, staleness оракула | Anchor `constraint`s + явні `require!` |
| **Versioned accounts** | Поле `version` у кожному PDA | Міграції без redeploy-паніки |

Anchor-специфіка: PDA-seeds як «індекс» (адреса обчислюється, не шукається); `remaining_accounts` для батчів; `zero_copy` для гарячих акаунтів; `init_if_needed` **не** використовувати для акаунтів із грошима (клас відомих вразливостей); усі CPI — з явною перевіркою `program_id` venue.

## 7. Технічний стек

| Шар | Вибір | Чому саме це |
|---|---|---|
| Ончейн | **Rust + Anchor 1.0**, `ephemeral-rollups-sdk` (MagicBlock), `anchor-spl` | Стандарт екосистеми; ER-SDK дає делегацію й permissions двома макросами. *Конкретику по макросах і генерації IDL звіряти з актуальними доками 1.0* |
| Приватний стан | **MagicBlock PER** (Intel TDX); локально — `mb-stack` + QFS | Латентність 10–50 мс; локальна емуляція TEE без заліза |
| Ціни | **MagicBlock Pricing Oracle** (Pyth Lazer у ER) для маржі; venue використовує свій оракул для fill | Без latency-розриву між ціною і станом у ER |
| Venue | **Jupiter Perps** (база), **GMTrade** (перевірити першим — комісії), **Flash** (є `flash-sdk-rust` для читання ончейн-стану + `examples-v2`, MIT), Adrena | Peer-to-pool = CPI + детермінована ціна (ландшафт 1.5, 1.7) |
| Власний пул (гібридний режим) | Форк **`solana-labs/perpetuals`** — офіційна референсна реалізація перпів від Solana Labs; її ж форкнув Flash і довів до продакшену | Краща база, ніж форк Jupiter: читабельна, відоме походження, перевірена живим venue. Береться лише якщо йдемо в гібрид із власною ліквідністю |
| Session Keys | `magicblock-labs/session-keys`; звірити з форком `flash-trade/session-keys` | **Flash уже інтегрований із MagicBlock** (є і `magicblock-grpc-example` на Rust) — зовнішнє підтвердження стеку живим перп-DEX на Solana |
| Локальна розробка | **Surfpool** (форк mainnet із клонованими акаунтами venue) + власний keeper-емулятор; LiteSVM для юніт-тестів | Jupiter Perps немає на devnet |
| Бекенд | **TypeScript / NestJS**; **Postgres** — єдине офчейн-джерело правди (проєкція подій, outbox, партиції по дню); **BullMQ + Redis — тільки як брокер черг, не кеш** | Стек, у якому автор найшвидший. Redis не кешує стан: проєкція в Postgres уже швидка, а другий шар істини дає розсинхрон і баг «показали стару позицію після закриття» |
| RPC | **Власний мінімальний шар** (~150 рядків): два провайдери (Helius основний, Triton/публічний резерв), health-check, перемикання за помилками й таймаутами, **окремі клієнти для ризикового й користувацького контурів** | kitguard свідомо не використовуємо. Без цього шару перший збій RPC зупиняє crank |
| Мобільний | **Expo / React Native**, `@solana-mobile/mobile-wallet-adapter-protocol`, Expo SecureStore (session key), **Expo Notifications** | Шаблон Solana Mobile; MWA лише Android |
| WebSocket-клієнт | Патерн `ManagedWebsocket` із `bullet-rust-sdk` (MIT, є WASM-біндинги): автореконект, експоненційний backoff, **повтор підписок після реконекту**, детекція мертвого стріму, скидання backoff після стабільного аптайму, дедуп підписок | Рівно те, що потрібно мобільному клієнту, де з'єднання рветься при кожній зміні мережі й згортанні апки. Брати як референс або через WASM |
| Комплаєнс | **Elliptic** (AML/OFAC) + **Range** (Solana-нативний моніторинг); гео — PER-ingress | Той самий стек, що у Vanish; не збираємо GPS |
| Спостережуваність | **OpenTelemetry** (traces від клієнта до crank), Grafana/Loki або Axiom | Без трейсів async-флоу не дебажиться |
| CI/CD | GitHub Actions: `anchor test` (LiteSVM), Surfpool-інтеграційні, `cargo audit`, EAS Build для APK | Один пайплайн на програму, бекенд і апку |

**Чого свідомо немає в стеку:** ElizaOS/агентні фреймворки, власний матчинг, власний оракул, kitguard, Kubernetes (один-два контейнери на Fly/Railway достатньо до v1), GraphQL, **Redis як кеш-шар**.

**Про кеш окремо.** Кеш потрібен, коли джерело правди повільне. У нас джерело правди — ланцюг і PER, а офчейн-проєкція вже лежить у Postgres і на індексованих запитах віддає позицію за мілісекунди при нашому профілі (тисяча користувачів × кілька дій на день). Замість кешу — три індекси під гарячі запити (позиція за власником, відкриті позиції за ризиковим бакетом, події за позицією) і курсорна пагінація в історії. Єдиний виняток, де Redis як сховище стану виправданий — гарячі ризикові бакети, коли воркерів стане більше одного; до того моменту вистачає in-memory.

## 7.5 MEV: де ми вразливі й де ні

**Sandwich на відкритті позиції — ризик низький.** У пуловому venue ціна береться з оракула, а не з кривої; наша угода сама ціну не рухає, тож класичний сендвіч тут майже не заробляє. Price impact fee рахується формулою від розміру, а не від стану пулу після чужої угоди.

**Де ризик реальний:** депозит і виведення, якщо в них є конвертація (SOL→USDC) — це звичайний AMM-своп з усіма наслідками; і будь-які спотові ноги, якщо з'являться.

**Іронія агрегації:** омнібус робить угоди **більшими** за індивідуальні, тому там, де сендвіч усе ж можливий, ми жирніша мішень.

**Jito DontFront.** Додати read-only акаунт із префіксом `jitodontfront` у будь-яку інструкцію → блок-енджин змушує ставити нашу транзакцію на index 0 у бандлі, тобто front-run неможливий. Подавати через `https://mainnet.block-engine.jito.wtf/api/v1/transactions`, base64.

**Наше рішення, що суперечить офіційній рекомендації.** Дока радить унікальний dontfront-pubkey на застосунок, щоб розрізняти власне використання в ончейн-даних. Для нас це **фінгерпринт**: усі транзакції Dexxer стають позначеними спільним маркером, і трекеру достатньо шукати цей ключ, щоб виділити наш потік. Тому — **канонічний `jitodontfront111...111`**, яким користується багато хто: розчинятись у чужому потоці, а не маркувати свій.

**Обмеження, які треба знати:** працює лише через блок-енджин Jito (транзакції напряму до валідаторів не захищені), **не працює на devnet і localhost** — на Surfpool цю поведінку не перевіримо; для бандлів dontfront-транзакції мають бути суміжними на початку і ділити підписанта, тож якщо колись пакуємо ліквідації в бандл — усі підписує той самий crank-ключ.

**Головна лінія захисту лишається інша** (і дока це підтверджує): вузький slippage у кожному request, адекватні tips і priority fees, оптимізований CU.

## 8. Безпека — модель довіри, названа явно

- **Ключі користувача** — лише в Seed Vault; ми не бачимо їх ніколи. Session Key — окремий ключ з обмеженим scope, TTL і лімітом дій; виведення — лише на гаманець власника (урок GMX).
- **Адмін-ключі** — мультисиг (Squads) + timelock на upgrade і на зміну ризик-параметрів. Урок Drift ($295M): найбільша загроза — соціальна інженерія підписантів.
- **TEE-довіра** — називаємо чесно: приватність від трекерів, копі-ботів і від нас; не від Intel і не від оператора валідатора. Перевіряти атестацію коду (allowlist MRTD/RTMR), а не лише свіжість квоти. **І визнаємо вголос:** MPC-модель Arcium («хоча б один чесний вузол») криптографічно сильніша за нашу; ми обираємо TEE заради латентності й передбачуваної семантики відмов, а не тому, що він безпечніший.
- **Чому Arcium не в ризиковому контурі** — не лише через латентність MPC-раундів. Cerberus працює в моделі **detect-and-abort**: при виявленій помилці протоколу обчислення зупиняється, і застосунок мусить сам обробляти відмову, повтор і міграцію. Крок ліквідаційної перевірки, який іноді просто не відбувається, поки ціна рухається, — неприпустимий. **Де Arcium доречний:** періодичний **доказ платоспроможності омнібусу** — сума зобов'язань проти колатералю, порахована над приватними позиціями з публікацією лише підсумку. Рідкісне обчислення, публічний результат, криптографічна гарантія саме там, де вона найпотрібніша — у довірі LP і аудиторів. Кандидат на v2 (див. §9).
- **Venue-ризик** — успадковуємо повністю; концентрацію знижуємо лімітом експозиції на venue.
- **Оракульний ризик** — staleness per market (урок GMX), консервативний зазор між нашим порогом маржі і порогом venue.
- **Trustless exit** — користувач має змогу довести частку омнібусу й вийти без нашого бекенду й без кооперації PER-оператора (мінімум: `request_close` + `withdraw` працюють напряму через програму; максимум — доказ частки з коміту агрегату).
  **Механізм-референс: Sparse Merkle Tree exclusion proof** із Solana Private Channels (Foundation, MIT, відкритий GitHub) — escrow-програма приймає доказ і віддає кошти ончейн незалежно від того, чи живий офчейн-шар. Це саме той примітив, якого нам бракувало; листком дерева в нашому випадку є частка користувача в омнібусі на момент останнього коміту агрегату. Читати їхній escrow і SMT-механіку як референс; **цілком не брати** — не аудитовано, доступ permissioned (RBAC + JWT), і між депозитом та виходом стоїть централізований секвенсер.
- **Ротація viewer-ключів** — правило зі стандарту CB, яке легко пропустити: ротація діє лише на майбутні записи, **старі ключі треба зберігати** для історичного доступу аудитора. Клас помилки, що виявляється через рік.
- **Аудит** — обов'язковий до реальних грошей; для хакатону — `cargo audit`, Anchor security-чекліст, LiteSVM-тести на кожен перехід state machine.

## 10. Відкриті питання (закриваються кодом, не документом)

1. Чи витримує PER частоту оновлень `UserPosition` при 1k+ активних позицій і crank у кожному блоці.
2. Чи можливий детермінований доказ частки омнібусу з коміту агрегату (для trustless exit) без розкриття інших позицій.
3. Яке правило розподілу ADL найменш конфліктне для користувачів — pro rata простіше пояснити, за левериджем справедливіше.
4. GMTrade: чи справді ~0.5 bps і чи fill атомарний — це змінює пріоритет venue і половину §4.1.
5. Session Keys SDK у React Native — працює чи пишемо ончейн-частину самі.
6. **Percolator як ядро Опції 2:** чи є USDC-маржа (або лише coin-margined); чи делегуються акаунти позицій у PER без переписування слаб-структури; чи збирається під наш тулчейн (Anchor 1.0 проти їхнього Anchor v2 / Pinocchio entrypoint). Плюс перевірити відкритість Adrena як актуального форку `solana-labs/perpetuals`.
7. Solana Privacy Protocol (Rings, бета): чи тримає Custom Ring стан із частими оновленнями, чи є CPI ззовні, чи придатна бета для демо. Якщо так — кандидат на депозитно-маржинальний шар (нативне рішення Foundation важить у пітчі більше за своє).
8. SMT exclusion proof для trustless exit: що саме є листком (частка в омнібусі на момент коміту) і чи можна довести її, не розкриваючи інші позиції.

# Умовні ордери (03.10.2026)

Limit, Stop (вхід), Take-profit, Stop-loss, Trailing stop. Один механізм на все.

## Модель

- Ордери живуть у `Position.orders` — масив із `ORDER_SLOTS = 4` слотів, доданий **в кінець** лейауту `Position` (`state/order.rs`). Окремого акаунта нема, тому ордери успадковують приватність позиції: делегований PDA з `EphemeralPermission { owner, session, crank }`. Онбординг, делегування й permissions не змінились.
- **Вхідні** (`Limit`, `Stop`): позиція `Empty`; `size`/`margin` — що відкрити; `tp`/`sl` (0 = нема) стають живими reduce-only ордерами після виконання. Limit: long при `mark ≤ trigger`, short при `mark ≥ trigger`. Stop — навпаки.
- **Вихідні** (`TakeProfit`, `StopLoss`, `TrailingStop`): позиція `Open`; завжди закривають усю позицію; по одному на тип (повторний `place_order` замінює). TP/SL, що вже за mark, відхиляються (`InvalidOrder`). Trailing: `trail_bps ∈ [10, 5000]`, `extreme` — найкраща ціна від розміщення; стоп = `extreme ∓ trail`, округлення на користь трейдера не раніше дистанції (long вниз, short вгору).
- Маржа при розміщенні **не резервується**: перевіряється при спрацюванні. Ордер, що вже не влазить (`InsufficientMargin`, ліміти ризику), **скидається**, а не ретраїться вічно. Тимчасові умови (пауза, якість оракула, повне кільце розкриття) лишають ордер на місці.

## Виконання

Той самий per-position scheduler-таск, що й ліквідація (`liquidation_check`, week 5): `place_order` (ре)реєструє його (повторна реєстрація того ж `task_id` — оновлення, виміряно у week 5), `liquidation_check` після перевірки ліквідації викликає `run_orders`. Список акаунтів таска не змінився, тож уже зареєстровані таски підхоплюють нову поведінку без перереєстрації. Тригери — за `Market.mark`, з тими самими воротами свіжості/девіації оракула. Ліквідація йде **раніше** ордерів.

- Таск скасовується (`cancel_liq_task`), лише коли позиція закрита **і** ордерів нема.
- `finalize_close` стирає reduce-only ордери (OCO: спрацював SL → TP зникає). Вхідні переживають закриття.
- Виконання вихідного ордера — `CloseReason::User` (публічне розкриття не відрізняє ордер від ручного закриття).
- Після виконання вхідного решта вхідних ордерів скидається (одна позиція на ринок).
- `undelegate_user` обнуляє `orders` до коміту на L1.

## Інструкції

`place_order(kind, side, size, margin, trigger, trail_bps, tp, sl)`, `cancel_order(slot)` — контекст `Trade` (13 акаунтів), підпис session/owner, споживають по одній дії сесії.

## Міграція

`Position` виріс (+208 Б). Уже делеговані devnet-позиції коротші й не десеріалізуються — потрібен ре-онбординг (`undelegate_user` зі старого білда → `close_exited_user`, або новий гаманець). Клієнтський `decodePosition` толерантний до старого розміру (`orders = []`).

## Не виміряно (потребує devnet-tee)

Реєстрація таска з `place_order` на порожній позиції; виконання вхідного ордера планувальником; вартість CU зростання `Position` на кожен тік. У LiteSVM Magic Program відсутній, тому покрито лише логіку (`tests/litesvm/tests/orders.rs`, 18 тестів).

## Поза обсягом цієї ітерації

Margin mode Isolated/Cross і Borrow Rate (пункти 2–3 беклогу) — не робились. Частковий TP/SL (на частку позиції), резервування маржі під вхідні ордери, ордери в `crank_tick` relayer-а.
